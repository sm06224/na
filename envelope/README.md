# `envelope`

### 信頼性包絡線コントローラ — ゼロ故障フリートの予備品計画

同一機器 数千台・設計寿命 40 年・故障実績ゼロ。**予測できないものを予測せず、境界（包絡線）で制御する。**<br>
仕様書 v2.0「信頼性包絡線制御モデル」の実装 兼 数値検証。依存ゼロ・オフライン単一 HTML。

</div>

---

## これは何

「まだ 1 台も壊れていない 3,000 台のために、予備品をいくつ・いつ買うか」に答える道具です。

普通のやり方（故障データからワイブル推定）はここでは**原理的に不可能**——ゼロ件からはどんなパラメータも推定できない。仕様書 v2.0 はそこで発想を変えます：

1. **宣言する**（§2-P3）——「設計寿命 40 年で 30% が壊れている」というアンカー F_a と、機械摩耗の経験的な形状範囲 β∈[2,5] を、推定値ではなく**計画仮定として宣言**する
2. **包絡線を張る**（§3.2）——宣言したバンド内の全ワイブル曲線をスイープし、各年の最悪値で境界を引く
3. **制御する**（§6）——実績が境界に近づいたら**調達リードタイム L 年ぶん手前**で鳴るトリガー（T1/T2/T3）で動く。予測の的中ではなく、**破られたとき早く気づける設計**が主眼

`envelope/index.html` を開くと、納入 CSV とパラメータを流し込むだけで、包絡線・実績・トリガー線・予備品数 P・感度分析まで一画面に出ます。すべての数字の脇に「なぜ」の注記（仕様の節番号つき）。

## 使い方

```bash
cd envelope
node --test tests/*.test.js   # 仕様の主張を数値で裏取り（11 tests）
node build.js                 # → dist/envelope.html（自己完結・オフライン単一 HTML）
```

入力（§8）：
- **納入コホート** CSV `納入年,台数`（例は [`examples/fleet.csv`](./examples/fleet.csv)）
- **故障実績** CSV `年,累積故障数`（任意。包絡線と重ねて描く）
- パラメータ：F_a・T_design・βバンド・L（調達リードタイム）・k_s（安全係数）・α（T1 係数）・現在年

出力：累積包絡線＋T1 線、単年度包絡線＋T2 線＋キャパ基準＋調達先行窓、ピーク（年・台数・支配 β）、プール予備 P、λ 上限（rule of three）、F_a/L 感度表、混合平坦化チェック、年次数表。

数式の導出と意味の解説（TeX）は **[MATH.md](./MATH.md)** に：ワイブル族とハザード、アンカー逆算、コホート畳み込みと平坦化、包絡線の支配 β、P と R_L、rule of three の導出、トリガー T1/T2/T3 と WeiBayes、混合平坦化、感度の向き。

## 調査結果 — 仕様 v2.0 の正しさ検証ノート

テスト（[`tests/model.test.js`](./tests/model.test.js)）が仕様の主張を一つずつ数値で裏取りした。**各テスト名は仕様の節番号を引く。**

### 確認できた主張

| 仕様 | 主張 | 検証結果 |
|---|---|---|
| §3.2 | アンカー逆算 η = T/(−ln(1−F_a))^{1/β} | 例示値 β=2→67.0 / β=3→56.5 / β=5→49.2 を再現。全 β で F(40)=F_a 厳密 |
| §3.2 | 40 年着地 3,000×0.30=900 台 | D(2050)=900.000…（一括納入 2010） |
| §3.2 | 支配 β は評価量で異なる | 累積のアンカー手前は低 β が上、単年度ピークは高 β（β=5 は β=2 の 1.5 倍超）。**包絡線ピークは常にバンド上限 β から出る** → 単一 β を選ばずスイープする設計は必須 |
| §4 | コホート畳み込みは平坦化 | 5 年分散納入は総量不変（±2%）でピークだけ低下。平行移動（v1 方式）に対応する物理はなく、廃止は妥当 |
| §9.4 | 環境不均一はさらに平坦化 | η±20% の 50:50 混合でピーク比 < 0.95 → **単一ワイブルは保守側** |
| §3.3 | rule of three | 45,000 台年ゼロ → λ ≤ 6.7×10⁻⁵/台年、年間期待 ≤ 0.2 台。**偶発域限定**（摩耗域には無力）という但し書きが要点 |
| §9 | 感度の単調性 | F_a↑ → maxD・P 単調増、L↑ → T1・R_L・P 単調増 |

### 曖昧・穴 → 本実装での解決（宣言）

| 箇所 | 問題 | 解決 |
|---|---|---|
| §5 R_L | 「ピーク近傍 L 年分の合計」は**窓の置き方が未定義** | 保守側に倒し **R_L = annMax の L 年転がし和の最大値**（最悪の L 年窓）と定義 |
| §6.2 T2 | しきい値（バンド下限 d(y)）は運用初期ほぼ 0 → **故障 1 件で発火** | rule of three の年間期待上限を**床**として敷く。偶発ノイズで発火せず、共通原因の検出は T3 が受け持つので保守性は失わない |

曖昧さは黙って埋めず、**解決を宣言して残す**（このモデル自身の流儀 §2-P3 に合わせて）。

## アーキテクチャ — なぜこの形か

```
envelope/
├─ index.html          画面の器。数字の脇に「なぜ」の注記（仕様の節番号つき）を散りばめる
├─ MATH.md             数式の導出と意味（TeX）。仕様 → 実装の橋
├─ js/core/model.js    数理コア。仕様の各節と 1:1 対応・純粋関数・決定的・DOM/ネット非依存
│                        → だからテストで数値まで固定でき、どの環境でも同じ答えが出る
├─ js/ui/charts.js     包絡線 → SVG 文字列（純粋）。帯＝バンド min–max、状態色は警戒/深刻のみに予約
├─ js/ui/main.js       配線だけ：入力を読み、コアを呼び、描く。DOM を触るのはこの層だけ
├─ build.js            import/export を剥がして単一 HTML へ（§8「単一ファイル・外部依存なし」）
├─ examples/fleet.csv  納入コホートの例
├─ dist/envelope.html  ビルド済み。この 1 枚をコピーすれば現場のローカル PC で動く
└─ tests/model.test.js 仕様の「正しさ調査」本体。テスト名 = 仕様の節番号
```

設計上の約束は [studio](../studio/) と同じ：**コアは DOM もネットワークも知らない。同じ入力からは寸分たがわず同じ答え（決定的）。**

## モデルの適用範囲外（§7）

共通原因・系統的故障（設計欠陥・ロット不良）は**量を予測せず T3 で検出して外へ渡す**。個体の故障時期は言わない。偶発域は上限のみ。1 件目の故障が出たら WeiBayes（β 固定・η 最尤）で宣言値の点検を始める（§6.3）。
